# Temporal Workflow Architectural Blueprint

## 1. System Architecture & Coding Guidelines
This document serves as the technical specification for generating Temporal workflows and activities in a C# .NET 8 environment. The system strictly adheres to **Domain-Driven Design (DDD)** and **Clean Architecture (Hexagonal)** principles.

When generating code from this blueprint, the AI MUST adhere to the following architectural constraints:

### Constraint A: Strict Layering
* **Domain Layer:** Pure C#. Zero external dependencies. Contains Aggregates, Entities, and Value Objects. Cannot reference Temporal.
* **Application Layer:** Contains Temporal Workflows (acting as Process Managers/Sagas) and Activity Interfaces (Ports). Workflows orchestrate domain models but contain NO business rules.
* **Infrastructure Layer:** Implements the Activity Interfaces (Adapters). This layer handles all Database I/O (Entity Framework/Dapper) and External API communication (HttpClient).

### Constraint B: Activity Granularity & Idempotency
To prevent distributed systems bugs during Temporal retries, Activities must be strictly segregated by side-effect boundaries:
1. **External Reads:** Activities that fetch data from 3rd-party APIs must be read-only.
2. **Domain Writes:** Activities that modify state must accept data, execute pure Domain logic, and save to the database. These writes MUST be idempotent (e.g., safe to retry without corrupting state).
3. **Never combine** a 3rd-party API call and a Database Save in the same Activity.

### Constraint C: Workflow Determinism
Workflows must be strictly deterministic.
* Do NOT use `Guid.NewGuid()`; use `Workflow.NewGuid()`.
* Do NOT use `DateTime.UtcNow`; use `Workflow.UtcNow`.
* Do NOT instantiate Domain objects or execute business logic directly inside the Workflow class.

## 2. Workflow Blueprints

### Workflow 1: Provider Credentialing & Onboarding
**High-Level Complexity:** Extreme. This is a long-running workflow (Saga) that can last weeks. It requires orchestrating unreliable 3rd-party government APIs, pausing for long durations without consuming compute, and handling human-in-the-loop manual overrides.

**Workflow Name:** `ProviderCredentialingWorkflow`
**Expected Signals:** `ManualReviewCompletedSignal`

**Actions / Activities:**
1. `FetchMedicalBoardLicenseAsync` (Read-Only)
    * *Detail:* Calls external state board APIs. High retry limit (e.g., 50 attempts with exponential backoff) due to flaky government servers.
2. `EvaluateAndSaveComplianceAsync` (Idempotent Write)
    * *Detail:* Takes data from Step 1, loads the `CredentialEvaluation` domain aggregate, evaluates the rules, and persists to the database.
3. `RequestManualReviewAsync` (External Notification)
    * *Detail:* Sends an alert to a compliance officer. The workflow then uses `Workflow.AwaitAsync()` to sleep until the `ManualReviewCompletedSignal` is received.
4. `ActivateProviderProfileAsync` (Idempotent Write)
    * *Detail:* Loads the `Provider` domain aggregate, updates status to Active, and persists.

### Workflow 2: Travel & Logistics Orchestration
**High-Level Complexity:** High. This workflow models a distributed Saga requiring **Compensating Transactions**. If a downstream step fails, the workflow must catch the failure and dynamically execute rollback activities to undo previous steps.

**Workflow Name:** `TravelLogisticsSagaWorkflow`

**Actions / Activities:**
1. `BookFlightAsync` (Idempotent Write / External API)
    * *Detail:* Calls airline API. Must use a deterministic Idempotency Key generated by the workflow.
2. `BookLodgingAsync` (Idempotent Write / External API)
    * *Detail:* Calls hotel/housing API.
3. `CancelFlightAsync` (Compensating Action)
    * *Detail:* Executed ONLY if `BookLodgingAsync` fails or the assignment is canceled. Refunds or voids the flight ticket.
4. `CancelLodgingAsync` (Compensating Action)
    * *Detail:* Executed to undo lodging reservations.
5. `NotifyTravelerAsync` (Read-Only/Notification)
    * *Detail:* Dispatches SMS/Email with the final itinerary or cancellation notice.

*AI Instruction:* Use a native C# `try/catch` block within the workflow. If `BookLodgingAsync` throws an ActivityException, the `catch` block must explicitly invoke the `CancelFlightAsync` activity before terminating the workflow.

### Workflow 3: Provider-to-Facility Matching Engine
**High-Level Complexity:** High. Solves a distributed concurrency and state synchronization problem. Multiple matching workflows may be running simultaneously for the same provider, requiring real-time state termination via Signals to prevent double-booking.

**Workflow Name:** `PlacementMatchingWorkflow`
**Expected Signals:** `OfferAcceptedSignal`, `OfferRejectedSignal`, `ProviderMatchedElsewhereSignal`

**Actions / Activities:**
1. `CalculateMatchScoreAsync` (Read-Only)
    * *Detail:* Queries database for provider availability and facility requirements.
2. `ProposeAssignmentAsync` (Idempotent Write)
    * *Detail:* Updates the database to mark an offer as "Pending" and notifies the user.
    * *Note:* The workflow now blocks using `Workflow.AwaitAsync`, waiting for one of the three Signals.
3. `CommitAssignmentAsync` (Idempotent Write with OCC)
    * *Detail:* Executed if `OfferAcceptedSignal` is received. Must implement Optimistic Concurrency Control (OCC) using an ETag or Version column. If the provider was booked by another process in the last millisecond, this activity fails, triggering a retry or compensation.
4. `RevokeOfferAsync` (Compensating Action)
    * *Detail:* Executed if `ProviderMatchedElsewhereSignal` or `OfferRejectedSignal` is received.

---

### Workflow 4: Time Ingestion, Payroll, and Billing
**High-Level Complexity:** Extreme financial risk. High-throughput pipeline requiring strict adherence to idempotency. Network drops during bank transfers must not result in duplicate payments.

**Workflow Name:** `TimesheetProcessingWorkflow`

**Actions / Activities:**
1. `ValidateTimesheetRulesAsync` (Idempotent Write)
    * *Detail:* Loads `Timesheet` domain aggregate, calculates overtime/on-call rules based on state labor laws, and persists the approved state.
2. `CalculatePayrollAndTaxesAsync` (Idempotent Write)
    * *Detail:* Generates the payroll ledger entry.
3. `SubmitBankTransferAsync` (Strict Idempotent External API)
    * *Detail:* Calls external payment gateway (e.g., Stripe/ACH).
    * *AI Instruction:* The workflow MUST pass `Workflow.Info.WorkflowId` or a `Workflow.NewGuid()` as the `Idempotency-Key` header to the activity so the payment gateway drops duplicate requests caused by Temporal retries.
4. `GenerateAndSendInvoiceAsync` (Idempotent Write)
    * *Detail:* Calculates facility bill rates and dispatches the invoice to the ERP system.
